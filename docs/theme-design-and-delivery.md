# 完整主题设计与交付规范

> 本文是 babycare 新主题的唯一执行规范，覆盖方向提案、完整方案、ImageGen 制作、图片后处理、代码接入、技术验收与提交。
>
> 旧的“经典轻量 Hero”与“天气主题”流程已停止使用。以后新增主题默认都是一套完整视觉系统，不再只复制背景图或沿用旧主题模板。

文档版本：2026-08-31

## 1. 完整主题的定义

一套新主题必须同时包含：

- 4 张不同时段的 Hero：清晨、白天、傍晚、夜晚。
- 4 枚快捷记录图标：喂奶、排便、护理、其他。
- 6 枚今日待办图标：用药、推拿、洗澡、护理、疫苗、生长。
- 5 枚底部导航图标：今日、记录、AI、趋势、档案。
- 1 张主题列表缩略图。
- 浅色与深色两套页面配色。
- 与共享天气系统兼容的表现。
- 必要且轻量的时段动态。

基础资源共 **20 张**。只有背景或只有一组图标的方案不再作为“新主题”交付。

代码原生轻量主题属于明确例外：当主题使用系统 Emoji 或项目已有线性图标承担全部功能图标时，可以只交付 4 张 Hero 与 1 张缩略图。此类主题必须使用独立 `iconPack`、在资源校验脚本的白名单中登记，并保证记录列表、弹窗、预览和导航均不回退到其他主题图片；普通图片型新主题仍严格执行 20 张完整交付。

### 为已有主题新增背景方案

已有完整主题可以继续扩展背景方案，不重复制作图标或主题配色。每套新增背景只包含：

- 4 张不同时段的 Hero：清晨、白天、傍晚、夜晚。
- 1 张用于背景选择器的缩略图。
- 对现有天气遮罩、时段动态、排版和移动端裁切的兼容。

默认背景与推荐背景分开维护：

- `defaults.bg` 只决定首次使用主题或清除自定义覆盖后的默认选中项。
- `recommendedBgs` 决定该主题“推荐背景”区域展示哪些背景，可以包含多个。
- 默认背景必须出现在 `recommendedBgs` 中，并排在第一位。
- 新增推荐背景不得自动替换默认背景，也不得改变用户已经保存的背景选择。
- 推荐关系只属于当前主题，不影响全局“其他背景”列表。

例如「水果蛋糕」主题：

```ts
defaults: { bg: 'hero-fruit-cake' }
recommendedBgs: ['hero-fruit-cake', 'hero-candy-workshop']
```

此时推荐区域同时展示「水果蛋糕」（默认）和「糖果工坊」（新增），用户已保存的选择不变。

## 2. 不可破坏的全局规则

- 不改变信息架构、业务流程、功能名称、核心操作位置和组件尺寸。
- 中文主题名优先使用 **4 个字**；英文印章简短，只作装饰，不承载关键信息。
- 新增完整主题默认排在主题列表最上方，按“最新在前”维护；`THEMES` 必须头部插入，对应的背景和图标方案也应放在各自完整主题区域的最前面，系统默认项不受此规则影响。
- 四张 Hero 必须是“同一世界、不同事件与镜头，主体可以一样，也可以不同”，不能只是同一不变的主体换光线或滤镜。
- 天气判断全主题共用。默认不重复生成晴、阴、雨等七套背景图。
- 图标必须在图片资源中校准大小和位置，不用主题专属 CSS 修正单枚图标。
- 浅色与深色模式只改变颜色、阴影和表面层级，不改变布局。
- 新主题的浅深模式各只定义 6 个基准色：`--theme-page`、`--theme-card`、`--theme-brand`、`--theme-ink`、`--theme-muted`、`--theme-complement`。组件语义色由 `theme-system.css` 统一派生，主题文件不得自行复制组件 token。
- `--theme-brand` 与 `--theme-complement` 的 hue 差需 ≥ 60°。前者绑定图表中的奶粉 + 白天，后者绑定母乳 + 夜间；`--orange` 不参与图表配色，仅用于疫苗状态、日历今日、报告徽章、浮动按钮等非图表语义。
- 首页「今日待办」标题文字色与整个待办区域背景色全主题统一，新主题不得染色。

### 「今日待办」保护边界

主题文件不得覆盖 `--token-today-plan-title`、`--token-surface-plan`，也不得为 `.today-plan` 直接或间接设置主题背景与标题色。浅色和深色最终计算色都应与经典主题一致。

## 3. 标准协作流程

### A. 方向提案

先提供 2～3 个差异明显的方向，每个方向说明：

- 四字主题名与一句话概念。
- 世界观和主要场景。
- 核心色彩与材质。
- 四张 Hero 的变化方式。
- 与已有主题的差异。
- 主要取舍。

必须明确推荐方向。用户选定后再写完整方案，不提前批量生图。

### B. 完整方案

使用第 4 节模板，确认以下内容：

- 四张 Hero 的主体、活动和构图是否真正不同。
- 左侧文案安全区和移动端安全主体。
- 动态落点及天气遮罩关系。
- 15 枚图标的具体语义、差异化配色和统一语言。
- 浅色与深色页面配色。
- 资源数量与实现成本。

只有完整方案确认后才进入制作。

### C. 视觉制作

执行顺序：

1. 先制作一张代表性 Hero，验证画风、世界观、左右构图和文字可读性。
2. 连续制作另外三个时段；保持世界一致，但更换主体、事件和镜头。
3. 先制作 4 枚快捷图标，验证透明背景、材质、视角和视觉体量。
4. 按同一母提示词制作 6 枚待办和 5 枚导航图标。
5. 批量完成透明处理、裁切和色彩空间转换；按分组 Alpha 加权可见面积统一视觉体量并校准重心后，再导出 WebP。
6. 从最能代表主题的一张 Hero 制作缩略图；联系表仅在用户要求协助视觉检查时制作。

制作过程中保留一份临时资产清单，记录每张交付图对应的生成结果、用途和最终文件名。交付说明中至少写明使用的生图模式、提示词组概述、最终导出规格和项目保存路径，方便后续返修；临时源图和联系表默认不提交仓库。

已确认的方案只要生成结果没有明显跑题，可连续完成，不需要逐张确认。

### D. 接入与验收

按第 9 节接入代码，并执行第 10 节对应级别的检查。

### E. 提交

确认改动边界后使用单一目的的中文 Commit：

```text
功能(主题): 新增{主题名}完整主题
```

保留并区分工作区已有改动，提交中不混入无关内容。

## 6. Hero 设计与生图规范

### 构图

- 最终比例固定为 2.5:1。
- 左侧约 50%～55% 的画面保持低细节，供白色标题、日期、天气和状态文字使用。
- 主要叙事放在右侧 60%～90%，但不能紧贴右边、顶部或底部。
- 右侧主体在手机端 `cover` 裁切后仍应可辨认。
- 不在图片中生成文字、Logo、UI、边框或水印。

### 四时段的连续性与变化

必须统一：

- 绘画媒介、材质语言和轮廓风格。
- 世界观规则、建筑或物件设计语言。
- 颗粒、景深和光影逻辑。

必须变化：

- 主体物件或主要空间。
- 角色行为或场景事件。
- 镜头角度及前中后景关系。
- 时间对应的光照和局部重点色。

### Hero 提示词骨架

```text
Use case: stylized-concept
Asset type: responsive web app Hero background, final crop 1080×432
Primary request: create the {time period} scene for the “{theme}” theme
Scene/backdrop: {scene}
Subject and activity: {unique subject and event for this period}
Style/medium: {shared style and medium}
Composition/framing: very wide 2.5:1 landscape; keep left 46% calm and low-detail for white UI copy; place the narrative focus in the right 52–90%; keep the focal point safe for mobile cover crop
Lighting/mood: {time-specific lighting}
Color palette: {palette}
Materials/textures: {shared materials}
Weather compatibility: preserve readable environmental areas for shared weather overlays
Constraints: no legible text, logo, UI, watermark or border; do not repeat another period’s subject, activity or composition
```

如果生成服务不支持 2.5:1，先生成更大的横图，再以右侧主体和左侧文字安全区为基准裁切到 1080 × 432，不能简单居中裁切。

## 7. 图标设计、透明图与后处理

### 统一语言与语义

- 图标是小尺寸功能识别物，不追求过度精细；优先清楚的轮廓和少量大色块。
- 同一主题统一材质、视角、描边、光源、阴影硬度和细节密度。
- 每枚图标使用 2～3 个主色，可加入一个独立识别色，避免全套颜色过于接近。
- 排便默认用“纸尿裤＋便便”表达，避免只画抽象符号。
- 推拿默认表达中式婴幼儿推拿，可使用手势、穴位或玉质刮痧板，避免按摩床、精油等西式 SPA 语义。
- “其他”不得因为主体结构复杂而显得更小；“记录”也没有固定缩小规则。全新生成的图标一律重新按视觉体量校准。

### 视觉体量与重心

- 先清理游离像素并裁掉透明空边，再放回 256 × 256 透明画布。
- 画布和最长边一致不等于视觉大小一致。快捷与待办共用一组基准，底部导航单独校准。
- 以每组 Alpha 加权可见面积的中位数为目标缩放，同组差建议控制在 8%～10%；常规包围盒约占画布 70%～80%。
- 细长、镂空、浅色主体可略大；厚重、深色、高填充主体可略小，数值之后仍以光学观感为准。
- 外接框中心建议落在画布中心 1～2px 内；非对称组合按整体视觉重心居中。
- 调整后重新检查 Alpha、边缘和 256px 辨识度。问题直接修图片，不新增单枚图标 CSS 补丁。

### 直接生成透明图

图标优先由 ImageGen 直接输出真实透明背景。透明输出通常更慢，因此只先用 1 枚代表图验证，不在整套图标上逐张等待和反复试错。

```text
Use case: stylized-concept
Asset type: square app icon on a genuinely transparent background
Primary request: create one {function} icon for the “{theme}” theme
Subject: exactly {object or compact object group}
Style/medium: {shared icon style}; clean compact silhouette; low-to-medium detail; consistent {front or 3/4} viewpoint
Composition/framing: centered; optical visual mass about 72% of the square canvas; balanced transparent padding; visually align with the icon set rather than using identical geometric bounds
Lighting/mood: soft upper-left light; short contained lower-right shadow
Color palette: {2–3 function colors}
Outline: {shared outline color and weight}
Constraints: genuinely transparent background; RGBA output with real alpha; no checkerboard, solid backdrop, colored square, badge, border, text, letters, numbers, logo, watermark or photorealism; exactly the described object
```

### Alpha 校验

生成后检查：

1. 源文件为 RGBA 且存在真实 Alpha 通道。
2. 四角为完全透明像素。
3. 在浅色、深色和高对比底上检查白边、黑边、棋盘格、游离像素和主体缺口。
4. 清理远离主体的小连通区域后，再计算包围盒和视觉重心。
5. 导出 WebP 后重新检查 Alpha 和 256px 下的辨识度。

本地处理适合裁切、连通区域清理、缩放、重心和色键；不要用宽松亮度阈值强抠白底，以免误删珍珠白、高光和浅色描边。

透明失败时依次处理：

1. 代表图失败后只再做 1 次服务端透明修复；仍无真实 Alpha、明显超时或返回棋盘格伪透明，就停止服务端逐张重试。
2. 改用与主体颜色无冲突的统一高饱和纯色底生成，再本地批量色键。背景必须无渐变、纹理和阴影；不符合时重新生成，不能宽松硬抠。
3. 先用 1 枚样图确认色键方向、主体完整、四角透明和边缘无染色，再批量处理其余图标。
4. 透明处理后统一校准视觉面积与重心，并重新执行三种底色检查。

对外进度说明保持简短、明确，可使用：

> 透明版生成通常更慢，目前只验证这一张。若仍无法得到真实 Alpha，将停止逐张服务端重试，改用统一纯色键背景生成并在本地批量转透明。

## 8. 天气与动态

共享天气状态为：晴、多云、阴、雨、雾、雪、雷雨。

新主题默认只调整：

- 天气层透明度、混合模式和遮挡关系。
- 粒子方向、密度或形态，使其符合主题空间语义。
- 阴雨状态下的明度与饱和度，避免主题被统一染成冷灰。

例如海底主题不能直接表现从天空落下的雨线，可把雨语义转为上浮气泡、水流和环境扰动，但仍需保留“当前是雨天”的可辨识反馈。

只有共享系统无法表达关键语义时才新增天气图片；这属于范围扩大，需要重新确认。

时段装饰动态规则：

- 每个时段最多 2～3 个动态点。
- 周期建议 5～10 秒，位移 2～6px，光照透明度变化 8%～15%。
- 只做局部光斑、蒸汽、薄雾、微粒、灯光呼吸等环境运动。
- 不快速闪烁、不大幅缩放、不持续弹跳、不让整张画面漂浮。
- 动态不能盖过天气反馈。
- 与背景具体物件对位的动态，使用与 Hero 相同的 `1080 × 432` SVG `viewBox` 和 `preserveAspectRatio="xMidYMid slice"`；坐标直接按原图定位，禁止另写桌面端 / 移动端百分比位置补丁。
- 纯光尘、雾气等无需严格对位的装饰才使用通用百分比动态容器。
- `prefers-reduced-motion` 下停止动画，并保留完整静态画面。

### 同名图片更新与部署缓存

- 默认与共享 Hero 会进入预缓存，其他主题按需缓存；后者只替换同名图片时，Service Worker 版本不一定变化。
- 已部署主题替换同名素材时，给该主题所有相关代码引用统一追加短内容哈希，例如 `asset.webp?v=1a2b3c4d`；同一资源不能同时存在多个版本值。
- 每次素材更新仍要运行 `npm run build`，并确认构建、查询参数和最终请求 URL 一致，不能只上传单张图片。

## 10. 技术验收流程

执行方只负责可自动判断的技术问题，主观视觉效果由用户验收。默认不使用浏览器逐页查看，不因视觉验收阻塞交付。

按改动类型执行最小检查集：

| 改动类型 | 必须执行 |
|---|---|
| 新主题或修改配置、样式、组件 | `npm test -- --run`、`npm run check:css`、`npm run build`、`git diff --check` |
| 只替换图片 | `npm run build`、`git diff --check` |
| 只修改文档 | `git diff --check` |

`npm run build` 已包含 `assets:check` 与 TypeScript 检查，无需在最终检查中重复运行。`assets:check` 负责数量、路径、尺寸、格式和 Alpha，不判断构图、边缘观感、重心、体量或配色。检查失败时只修复本次引入的问题；既有基线问题单独说明。最终只汇报结果、异常和需要用户关注的位置。

### 用户主要验收

- 四张 Hero 的题材、构图、裁切和整体观感。
- 图标大小、位置、颜色区分和功能辨识度。
- 浅色、深色页面配色以及图表主色与对比色。
- 动态强度、天气观感和其他主观视觉问题。
- 页面中的资源加载结果、主题切换效果及实际设备观感。

用户指出问题后，直接针对对应资源或页面修正，只执行与该次改动对应的技术检查。

仅在用户明确要求时，执行方才使用浏览器、截图或联系表检查指定页面、模式、天气或视口，不自动扩大为全量视觉回归。资源缺失、编译错误或测试失败直接按技术问题处理。

完成标准：资源与功能接入齐全、对应检查通过、用户接受视觉效果、无已知技术阻断，且改动未覆盖无关内容；之后按要求完成或等待中文单一目的提交。
